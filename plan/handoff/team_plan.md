# MiniSQL 四人分工与验收（定稿 v1.5）

> 修订日期：2026-09-08。配套文件：[公共契约 v1.5](contracts.md)、[工作流交接 v1.5](handoff.md)。
> 接口、格式和错误行为以公共契约为准；本文件明确负责人、协作边界和交付验收。
> 分工原则：每人负责一条贯穿编译、存储或执行集成的职责线，通过冻结接口、公共类型和测试替身并行开发。
> 当前进度：v1.5 文档已定稿，M1 骨架、公共类型、接口存根和最小契约测试已建立；业务模块真实现与四人会签未标记完成。运行方式见 [工程说明](../../database_system/README.md)。

---

## 1. 总体分工与协作方式

```text
SQL 文本 → A：Lexer → B：Parser / AST → C：语义检查 → D：计划 / 优化
                                                            ↓
                                                     D：执行引擎
                                                            ↓
                                              B：表、记录、页链、槽
                                                            ↓
                                              C：物理页、缓存、空闲链

C：Catalog 贯穿名称解析与系统目录持久化，通过 B 的表级接口访问目录记录。
D：runtime 负责生命周期、语句分段、错误恢复和逐语句编译／执行。
A：CLI 调用 runtime，负责统一展示、用例执行器和端到端验证。
```

| 负责人 | 阶段一：SQL 编译器 | 阶段二：页式存储 | 阶段三：数据库系统 | 贯穿职责 |
|---|---|---|---|---|
| A | 词法分析、Token | 用例基础设施、日志展示约定 | 批处理命令行、端到端测试 | 用例库、用例执行器、运行说明 |
| B | 语法分析、AST | 记录序列化、表映射、页链和槽 | 行级存储接口与记录标识 | 文法、AST 和记录结构说明 |
| C | 语义分析、类型规则、Catalog | 物理页、缓存和空闲页链 | 系统目录持久化、重启恢复 | 元数据生命周期 |
| D | 计划生成、优化 | 集成替身及存储接口联调 | 表达式求值、执行算子、顶层编排 | 公共异常、结果类型、持续集成 |

- 允许导入公共契约类型，并通过接口和依赖注入协作；不得依赖其他模块的私有实现。
- `sql_compiler/errors.py` 是异常类的唯一定义处，由 D 维护；禁止复制同名异常类。`utils/results.py` 的公共结果类型同样由 D 维护。
- AST 由 B 定义，Catalog 和类型规则由 C 定义，Token 由 A 定义，计划结构由 D 定义。使用方直接导入对应公共定义，不另建副本。
- 用存根和测试替身隔离尚未完成的模块；并行开发不等于没有运行时依赖。D 负责应用装配和调用顺序，B 通过 C 的页接口访问物理存储，C 的 Catalog 通过注入的 B 存储接口访问系统目录。

## 2. A：词法、命令行和测试基础设施

**职责理由**：输入扫描、文本展示和输出断言由同一负责人维护，避免命令行与用例执行器产生两套格式。

| 交付物 | 主要文件 | 必须满足的边界 |
|---|---|---|
| 词法分析 | `sql_compiler/lexer.py`、`tests/test_lexer.py` | `tokenize(text) -> list[Token]` 完整扫描一次；成功含唯一全局 EOF；失败抛公共 `LexerError`，保留全部诊断 `errors` 和有效 `tokens`。 |
| 批处理命令行 | `cli/main.py` | 负责参数、UTF-8 文件／标准输入读取、结果展示和退出码；输入读取至 EOF，不提供 REPL 提示符。 |
| 用例执行器、端到端测试 | `tools/case_runner.py`、`tests/test_e2e.py`、`tests/cases/` | 维护 `.sql + .expected` 对比及标准错误、退出码断言；D 负责将这些检查接入持续集成。 |
| 交付说明 | `README.md`、实践报告汇总 | 汇总运行方式、测试结果和失败案例；各负责人提供自己模块的说明。 |

**命令行对接固定为**：先 `open_database()`，向 `run(text, catalog, storage)` 提交 SQL，最后 `close_database()`；CLI 不自行分段，也不分别调用 `compile_sql()` 或 `execute()`。

- `--mode compiler|database` 默认 `database`；`--data-dir` 默认 `data`。编译模式使用 `catalog.json`，数据库模式使用 `minisql.db`，不隐式迁移数据。
- UTF-8 输入允许 BOM，归一化换行。四个展示开关及其对应 `--no-*` 开关按契约命名，默认全部开启，重复指定以最后一次为准。
- 按顺序展示 Token、AST、语义成功提示、原始计划、优化计划、查询表头、查询行和执行消息；失败时先展示已完成阶段，再逐行输出诊断。词法失败不展示中间产物。
- 固定前缀为 `TOKENS:`、`AST:`、`SEMANTIC: OK`、`PLAN:`、`OPT_PLAN:`、`COLUMNS:`、`ROW:`、`RESULT:`。JSON 中文不转义、键排序、紧凑分隔，禁止非有限数字；标准输出使用 UTF-8 和 LF。
- 全部 SQL 成功退出 0，存在 SQL 失败退出 1；参数、输入文件、数据库初始化或关闭失败写标准错误并退出 2。缓存日志和统计走标准错误，不污染结果断言。
- `tests/cases/compiler/` 和 `tests/cases/execution/` 分别验证编译模式与数据库模式；用例执行器提供 `--suite compiler|execution|all`，默认 `all`。普通用例使用独立临时数据库，重启用例在同一用例内复用目录。

## 3. B：语法、AST 和行级存储

**职责理由**：AST 与记录序列化都要求精确定义结构、顺序和边界，由 B 统一维护逻辑结构到物理表示的约定。

| 交付物 | 主要文件 | 必须满足的边界 |
|---|---|---|
| 语法分析、AST | `sql_compiler/parser.py`、`sql_compiler/ast_nodes.py`、`tests/test_parser.py` | `parse(tokens) -> list[Stmt]` 首个语法错误即抛出，不做跨语句恢复；节点和 `to_dict()` 与契约一致。 |
| 文法文档 | `grammar.md` | Parser 完成时定稿，原样采用公共契约的 EBNF；实现必须与文法一致。 |
| 记录序列化 | `storage/record.py`、`tests/test_record.py` | INT 为小端有符号 32 位；VARCHAR 为 2 字节长度前缀和最多 255 字节 UTF-8；记录头固定为 0。 |
| 行级存储引擎 | `storage/storage_engine.py` | 管页 0 的表数和表映射、表页链、槽、记录标识和追加写入；通过 C 的页接口操作缓存和物理页。 |

**编译边界**：Parser 消费 D 分段后的 Token 切片，保留全文件行列号。空输入合法，单独分号报错；NULL 是保留关键字，由 Parser 拒绝。优先级从高到低为括号、乘除、加减、比较、NOT、AND、OR。非终结符入口失败用推导出的 FIRST 集，具体 `expect()` 失败用正在匹配的终结符，集合展示顺序固定。

**存储接口**：B 提供 `RecordId = tuple[int, int]`（页号、槽号），并实现契约中的 `StorageEngine.has_table/create_table/insert_record/scan_records/delete_record/flush/close`。扫描返回 `(RecordId, row)`，供执行器保留记录位置；面向用户的查询结果不暴露记录标识。

- 数据页为 4096 字节，页头 `<IHHII>` 共 16 字节，槽 `<HH>` 共 4 字节；第 `i` 槽位于 `4096-4*(i+1)`。单条记录最多 4076 字节，超限必须在修改页或分配页前拒绝。
- 删除只将槽偏移改为 `0xFFFF`，已分配槽数不减少；不复用墓碑槽，不跨页存放单条记录。插入从表尾页追加，空间不足时增加尾页。
- 页 0 采用 `<4sHHII>` 页头和 60 个 `<64sI>` 表映射条目；表名存小写 ASCII，短于 64 字节时补零。容量包含系统表，因此最多 59 张用户表。
- B 维护表数、表映射和表页链；C 维护物理页分配和空闲链。对共享的页 0 必须在最新缓存页上修改各自字段，保留其他字段。
- B 不承担 Catalog 语义验证或空闲链管理；向 C 的 Catalog 提供系统表的创建、插入和扫描能力，向 D 提供用户记录读写能力。

## 4. C：语义、Catalog、物理页和缓存

**职责理由**：Catalog 的名字解析、持久化和重启恢复需要统一规则，页存储与缓存则为这些规则提供底层读写能力。

| 交付物 | 主要文件 | 必须满足的边界 |
|---|---|---|
| 语义分析、类型规则 | `sql_compiler/semantic.py`、`sql_compiler/types.py`、`tests/test_semantic.py` | `analyze(stmts, catalog)` 只检查和标注，不注册或持久化表；按契约收集语义诊断。 |
| Catalog | `sql_compiler/catalog.py` | 统一大小写不敏感的名称解析；支持阶段一 JSON 后端、纯编译内存快照和阶段三系统目录后端。 |
| 物理页和缓存 | `storage/page.py`、`storage/buffer.py`、`storage/file_manager.py`、`tests/test_storage.py` | 维护物理页分配、释放、读写、缓存替换、刷盘、命中统计和空闲链。 |
| 系统目录持久化 | `sql_compiler/catalog.py` 及对应测试 | 经 B 的表级接口读写系统目录，校验已有数据库并在重启时恢复用户 Schema。 |

- INSERT 目标列必须无重复且完整覆盖表列，允许顺序不同；C 检查合法性，D 在执行时恢复为表结构顺序。浮点字面量的有限性由 B 在 Parser 转换时检查，C 按 UTF-8 字节数检查 VARCHAR 长度。
- C 保留 `read_page/write_page/get_page/flush_page/alloc_page/free_page/stats` 七个页接口，增加 `flush_all()`、`close()`；具体签名按公共契约实现。正常操作经过缓存；直接写盘成功后使对应缓存失效；关闭前写回全部脏页。
- 默认 LRU，提供 FIFO；日志和统计只写标准错误。空指针为 `0xFFFFFFFF`，空闲页前四字节保存下一空闲页号；分配优先使用空闲链，否则追加文件。禁止释放页 0 或仍在表链中的页。
- `__catalog__` 固定为每列一条记录：`table_name, column_name, column_type, ordinal, source_line, source_column`。前三列为 VARCHAR，后三列为 INT；序号从 0 开始，保存原始名字和源码位置用于重建 `ColumnDef`。
- 系统目录 Schema 直接定义，不记录系统表自身；用户 SQL 禁止创建或访问 `__catalog__`，用户表列表也不显示它。
- 新库按“初始化页 0 → 打开存储引擎 → 创建系统目录 → 加载 Catalog”启动；已有数据库缺系统目录时报损坏，不静默重建。
- `Catalog.create_table()` 在写入前完成重复名、保留名、结构及容量检查；数据库模式下由其调用 B 完成物理表及目录登记，成功写入、刷盘后更新内存目录。不得在 `analyze()` 中提前登记。

## 5. D：计划、优化、执行、公共类型和集成

**职责理由**：计划的生成与执行由同一负责人维护，应用编排集中处理阶段顺序、错误边界与结果保留，减少各模块重复实现流程。

| 交付物 | 主要文件 | 必须满足的边界 |
|---|---|---|
| 计划和优化 | `sql_compiler/planner.py`、`sql_compiler/optimizer.py` 及对应测试 | AST 转计划、常量折叠和布尔化简；不修改原始计划；规则名按首次触发顺序去重，循环至不动点。 |
| 公共异常和结果 | `sql_compiler/errors.py`、`utils/results.py` | 异常类型唯一；`StmtResult` 保留原有六字段并增加 `semantic_ok: bool \| None`。 |
| 纯编译入口 | `sql_compiler/__init__.py` | `compile_sql(text, catalog) -> list[StmtResult]` 使用目录内存快照，成功建表对后续编译可见，不写真实目录，首个失败语句抛异常。 |
| 执行器及求值器 | `engine/executor.py`、`engine/evaluator.py`、`tests/test_executor.py` | `execute(plan, catalog, storage) -> ExecuteResult`；支持 CreateTable、Insert、SeqScan、Filter、Project、Delete。 |
| 生命周期和编排 | `engine/runtime.py` | 实现 `open_database/run/close_database`，负责语句分段、恢复、阶段调用及产物保留。 |
| 持续集成 | 持续集成配置 | 接入模块测试、A 的用例执行器和端到端测试，维护检查入口；不重复维护另一套用例执行器。 |

对 A 暴露的生命周期与提交接口，以及供开发测试使用的纯编译接口统一为：

```python
def open_database(data_dir: str, *, mode: str = "database"
                  ) -> tuple[Catalog, StorageEngine | None]: ...
def run(text: str, catalog: Catalog,
        storage: StorageEngine | None = None) -> list[StmtResult]: ...
def compile_sql(text: str, catalog: Catalog) -> list[StmtResult]: ...
def close_database(catalog: Catalog,
                   storage: StorageEngine | None) -> None: ...
```

- `run()` 只调用一次 Lexer，按真正的分号 Token 切片，为每段添加局部 EOF，行列号保持全文件位置；将词法诊断归属到对应分段，含词法错误的段不进入 Parser。
- Parser 首错抛出，`run()` 负责跨段恢复。缺分号使截至下一分号的整个分段失败，不能凭第二个语句关键字恢复；空输入返回空列表。
- `run()` 捕获语句级错误并继续后续语句。编译错误按契约格式输出，执行错误为 `[EXECUTE] Error: reason`；多诊断按源码位置排序后用换行连接存入 `error`。
- AST 在语法成功后保存结构快照，语义标注不进入展示 JSON。词法失败无展示产物，语法失败保留 Token，语义失败保留 Token 和 AST，执行失败保留两份计划；成功完成语义阶段才展示 `SEMANTIC: OK`。
- `run(storage=None)` 是阶段一编译模式：每条 CREATE 完成全部编译阶段后，由 `run()` 提交传入的 Catalog；CLI 的 compiler 模式持久化 JSON，调用方指定的内存 Catalog 不写盘。数据库模式由执行器只调用一次 `Catalog.create_table()`；执行器不得再自行重复注册或创建物理表。
- INT 为有符号 32 位，整数除法向零截断；除零和运算溢出仅在实际求值时产生执行错误。AND、OR 从左到右短路。
- 常量折叠遇除零或溢出保留原子树；`x AND FALSE`、`x OR TRUE` 仅在折叠后的 `x` 不含算术节点时消除。优化前后必须返回相同结果或相同执行错误，不能因空表或短路改变错误时点。
- 扫描和过滤内部保留记录标识；DELETE 先完成全部筛选，再按记录标识标记删除，避免表达式错误导致部分删除。查询最终仍返回元组。

## 6. 三阶段里程碑与完成标准

| 里程碑 | 交付和验收 | 协作重点 |
|---|---|---|
| M1：仓库骨架与接口存根 | 已按 v1.5 建立模块、公共类型、函数存根和测试入口；本地最小契约测试通过，团队仍需核对并接受共同基线。 | 公共异常、结果和单语句连接器就位；业务入口保留明确存根，各人可用测试替身独立开发。 |
| 阶段一：编译器答辩 | 支持四类语句、词法／语法／语义诊断、计划和优化展示；编译模式按约定持久化 JSON 目录，纯编译函数无写入。 | B 保证文法一致，C 保证目录副作用边界，D 保证错误恢复和中间产物，A 固定输出。 |
| 阶段二：存储答辩 | 记录和页布局、表映射、跨页追加、墓碑删除、缓存替换与刷盘验证通过。 | B 管逻辑布局和页链，C 管物理页与缓存；重点测试容量为 1 的缓存和页 0 字段互不覆盖。 |
| 阶段三：数据库答辩 | CREATE、INSERT、带 WHERE 的 SELECT、DELETE 正确执行；关闭重启后表结构和记录可恢复。 | C 负责系统目录，D 负责执行与生命周期，B 负责行级正确性，A 负责端到端验收。 |

每人完成自己的职责线，需要模块检查通过、提交至少 15 条公共用例，并通过其他成员覆盖该模块的集成用例。总用例至少 60 条，每人及总库错误用例均不少于一半；阶段一验收时 compiler 套件须满足这些门槛，后续追加 execution 用例。不得把同一用例在多人的数量中重复计数。

| 验收主题 | 必须覆盖的场景 | 牵头与配合 |
|---|---|---|
| 分段与诊断 | 词法错误后继续后续语句、未闭合字符串、缺分号、空输入、单独分号、局部 EOF、全文件位置、多诊断逐行展示。 | A、B、D |
| 文法与语义 | `a=1 OR b=2 AND c=3`、NOT 优先级、NULL、FIRST／终结符诊断、`VALUES('Alice',1)` 类型双错、INSERT 重复列／缺列／列重排。 | B、C |
| 中间产物与目录 | 各阶段失败保留正确产物、执行失败后继续；纯编译不写真实目录，阶段一 CREATE 持久化 JSON，阶段三只登记一次。 | C、D，A 验证输出 |
| 物理边界与恢复 | 长列名结构重启恢复、第 59／60 张用户表边界、4076／4077 字节记录边界、跨页插入、删除首槽、删除重复值记录、关闭重启。 | B、C、D |
| 缓存与优化 | 缓存容量为 1、LRU／FIFO、关闭刷盘；空表、除零、溢出及短路表达式下，优化前后结果或执行错误一致。 | C、D |
| 命令行与测试隔离 | 开关及反向开关、文件与标准输入等价、BOM／换行、空结果集、输出格式与退出码；普通用例独立目录，重启用例内复用目录。 | A，D 接入持续集成 |

最终交付包括模块化源码、README 和运行说明、文法、AST／Catalog／Plan 结构说明、测试用例和结果、失败案例分析、实践报告。B 负责文法与 AST 说明，C 负责 Catalog 和页存储说明，D 负责计划与执行说明；各人撰写实践报告中自己职责线的章节，A 统稿。

## 7. 契约变更和集成规则

1. 允许提出契约问题和修改建议。后续变更必须先由四人全部审批，修改公共契约并递增次版本号，再同步本文件与交接文件；未经审批不得改变已冻结接口、格式或行为。
2. 对现有条款理解不一致时，先按公共契约核对；无法消除的歧义按同一变更流程形成明确裁决，不由单个模块自行决定。
3. D 发现某模块偏离契约时，由该模块负责人修正；若契约本身需要修改，先走四人审批，不用编排层兼容未经批准的变体。
4. 不得为使自己的代码运行而直接修改他人负责的模块；跨负责人修改通过变更请求或 PR 协作。公共类型的变更由 D 维护并同样遵守契约审批流程。
5. 文档定稿、源码完成、测试通过和四人审批分别记录，未实际发生的事项不得写成已完成。
