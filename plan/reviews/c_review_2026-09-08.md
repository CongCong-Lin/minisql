## 初次审查缺陷与证据（三项均已修复）

### 1. 中等优先级：长表达式泄漏原生递归异常

位置：[semantic.py](../../database_system/sql_compiler/semantic.py)，第 46–47 行；一元表达式第 52 行具有相同风险。

语义类型推导直接使用 Python 调用栈遍历表达式。独立复现中，900 项左结合加法可通过，1100 项会抛出 `RecursionError`。对应的平坦 SQL 只有约 2.2 KB，文法没有禁止这种长度。把比较右值换成 VARCHAR，也无法得到应有的语义类型错误。

复现代码在工程目录运行：

```python
from sql_compiler.ast_nodes import BinaryExpr, ColumnDef, LiteralExpr, SelectStmt
from sql_compiler.catalog import Catalog
from sql_compiler.semantic import analyze

catalog = Catalog()
catalog.create_table("t", [ColumnDef("a", "INT", line=1, column=16)])
expr = LiteralExpr(1, "INT", line=2, column=23)
for index in range(1, 1100):
    expr = BinaryExpr("+", expr,
                      LiteralExpr(1, "INT", line=2, column=23 + 2 * index),
                      line=2, column=22 + 2 * index)
where = BinaryExpr("=", expr, LiteralExpr(1100, "INT", line=2, column=2224),
                   line=2, column=2223)
analyze([SelectStmt("*", "t", where, line=2, column=1)], catalog)
```

影响：合法表达式不能完成语义检查；D 接入后若仅捕获公共编译异常，原生异常会打断语句恢复。依据为契约 §2.1 的重复表达式文法、§5.1 语义接口与 §7.1 公共异常边界。

修复建议：采用显式栈执行后序遍历，保留先左后右、错误位置与标注规则。增加至少 1500 项的合法算术链、类型错误链和逻辑链回归。不要单纯提高全局递归上限。

联调说明：B 的 `AST.to_dict()` 同样递归，完整流水线可能在更早的快照阶段触发该问题。需要与 B/D 一起处理；本轮真实复现的是 C 的公开 `analyze()`，没有声称已跑完整 SQL 流程。

### 2. 中等优先级：淘汰日志故障绕过公共异常体系

位置：[buffer.py](../../database_system/storage/buffer.py)，第 40–43 行，日志写入在第 42 行。

容量 1 时，先分配页 1、缓存页 0，再访问页 1 触发淘汰。如果标准错误输出的 `write()` 抛出 `OSError`，当前代码已删除旧缓存、增加淘汰次数，却尚未插入新页；异常直接泄漏，没有转换成 `ExecuteError`。

独立实验观察：异常类型为 `OSError`，不是 `ExecuteError`；缓存页数变成 0，淘汰次数已增加。标准错误输出被重定向到故障设备或管道断开时可能出现这种情况。已成功写回的脏页没有丢失，本项不应描述为已复现数据损坏。

复现步骤：

1. 用容量 1 创建 PageStore，调用 `alloc_page()` 得到页 1，再 `get_page(0)`。
2. 将标准错误输出临时替换为 `write()` 抛出 `OSError` 的对象。
3. 调用 `get_page(1)`，检查异常身份及缓存状态。

依据：契约 §9.3 要求 I/O 故障转成 `ExecuteError`，供上层统一处理。

修复建议：先完成缓存状态更新，再处理淘汰日志；日志写入失败按统一 I/O 错误策略转为公共异常，避免留下半完成状态。增加日志失败注入测试，检查缓存、计数、异常类型及后续可用性。

### 3. 中等优先级：直接目录 API 的重复列定位偏离契约

位置：[catalog.py](../../database_system/sql_compiler/catalog.py)，第 98–99 行。

契约 §4.2 明定：没有语句位置的 `Catalog.create_table()` 直接调用采用首个 ColumnDef 的位置。当前重复列分支传入重复列对象，因此采用后一列位置。

例如，首列 `ColumnDef("first", "INT", line=2, column=10)`，重复列 `ColumnDef("FIRST", "VARCHAR", line=5, column=30)`；内存、JSON、系统目录三个后端均实际报告 `(5,30)`，契约要求 `(2,10)`。错误在写入前发生，没有注册表或写入存储。

修复建议：区分公开建表入口和语义入口的定位策略。公开直接调用使用首列位置；`analyze()` 仍需准确定位重复的列定义。不能简单去掉 `_validate()` 中的列参数，否则会破坏语义阶段的已有准确定位。

测试缺口：现有“直接 API 使用首列位置”测试仅覆盖重复表和空列列表，重复列测试没有断言位置。应补三个后端的直接调用位置测试，并保留语义阶段定位后一个重复列的测试。

## 非阻断风险与后续开发事项

### 空闲链批量操作为平方级开销

[file_manager.py](../../database_system/storage/file_manager.py) 第 158、180 行每次分配／释放都完整遍历空闲链。容量 1 下依次复用 50／100／200 页，实测底层读取为 1326／5151／20301 次，呈平方级增长。

当前契约没有吞吐指标，普通 INSERT／DELETE 也不回收表页，因此这不是本轮功能验收失败项。后续引入大量回收或压缩操作时应优化：启动时完整校验，运行时维护可失效的链状态；公开整页覆盖元数据或空闲页后必须重新验证，不能牺牲现有损坏检测和调试写入一致性。

### 系统目录 I/O 失败可能留下部分物理状态

目录建表先创建物理表，再逐列写入元数据。中途失败可能留下物理表或部分列记录；现有元数据没有总列数或提交标记，不能保证检测缺失的尾部列，也不能通过当前 B 接口枚举所有孤立物理表。

这是契约明确不承诺 I/O 回滚的边界，不应将其认定为本轮 C 必须实现事务恢复。团队需在异常演示及报告中说明：正常完成和正常关闭后的持久化，与写入失败后的状态保证不同。若未来希望失败后可安全重试，应先共同调整契约和元数据格式。
